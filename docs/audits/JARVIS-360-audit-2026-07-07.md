## Executive summary

The application itself is structurally sound: no SQL injection anywhere in the reviewed code, permission checks are applied consistently apart from a handful of gaps, the TypeScript build is clean, session/cookie/CORS hardening is correct, production is up, healthy, and running the latest merged code, and 975 of 979 unit tests pass.

The risk is concentrated in five items, four of which are operational rather than code quality:

1. **Two live passwords are exposed** — the production login is already public on GitHub; the staging DB password sits in unpushed commits and would be published by the next `git push`.
2. **Production DB dumps are in git history on GitHub.**
3. **A month of work (226 commits) exists only on one machine**, with a dirty tree and no branch upstreams.
4. **An unauthenticated public endpoint can create legal contract documents** — not yet in production, but one merge away.
5. **Today's flagship feature (Hub PDF download links) is dead code** — it can never render due to a modal-unmount bug.

Everything else is fixable on a normal cadence.

## 2. High

### 2.1 EuroFib STORNO export math (feeds accounting directly)
- **Rows for cars the reversed advance never covered.** [routes_orders.py:1661](jarvis/accounting/facturare/routes_orders.py:1661) (single) and `:1853` (batch) loop over the storno's cars without checking `car["id"] in ri_line_ids`; the PDF path does filter (`:1380`). Partial/subset stornos book reversals against wrong cars, and the equal-split branch no longer sums to the reversed total.
- **Belegnummer divergence.** EuroFib numbers per (advance × car) row ([eurofib_xlsx.py:143](jarvis/accounting/facturare/generators/eurofib_xlsx.py:143)) while the PDF/UI number per car. A multi-advance storno consumes more Belegnummern in the export than exist on issued documents — unmatchable references and possible collisions with the next invoice range.
- **Rounding never cancels.** Advances export per-car amounts rounded to whole EUR (`:1696`), storno reversals to 2 decimals (`:1664`) — residues up to ±0.50 EUR/car remain on the konto. No largest-remainder reconciliation exists anywhere per-car shares are computed, so booked totals can differ from invoice totals by several EUR.

### 2.2 IDOR — foi-parcurs PDFs and contract detail
[pdf.py:8](jarvis/foi_parcurs/routes/pdf.py:8) and [contracts.py:199](jarvis/foi_parcurs/routes/contracts.py:199) are `@login_required` with **zero ownership/company scoping** — any authenticated user can enumerate integer ids and download any contract PDF (client name/phone PII). Freshly relevant: commit `071c9b11` surfaces these URLs to end users in HubFormModal.

### 2.3 The Hub success screen / PDF links can never render
[Hub/index.tsx:1544](jarvis/frontend/src/pages/Hub/index.tsx:1544) sets `successData` then calls `onSubmitted()`; the parent (`:1496`) immediately does `setOpenSlug(null)`, unmounting the conditionally-rendered modal before the thank-you screen and "Download Legal/Custom PDF" links (`:1570-1590`) ever paint. Users only see the generic toast — the headline feature of today's top commit does not fire. Fix: close the modal from the success screen's button, not in `onSubmitted`.

### 2.4 Missing dependency `cryptography`
Imported at module top in [auth_service.py:17](jarvis/core/connectors/efactura/services/auth_service.py:17) but absent from `requirements.txt` — e-Factura certificate auth raises ImportError on any fresh install.

### 2.5 Repo bloat: 246.55 MiB, ~90% from one file
`jarvis/static/downloads/jarvis.apk` has 19 historical versions totaling ~221 MiB. Also tracked: 166 screenshot PNGs (109 at root), 3 `.pptx` decks, `output/`/`tmp/` artifacts, two zips, and ~270 stale `jarvis/static/react/` build files (ignored-but-tracked). The same history rewrite that purges `backups/` (§1.3) can reclaim ~90% of the repo.

## 4. DigitalOcean production environment

**Topology (confirmed via API):** one DO app `jarvis` (FRA) hosts both environments —

| Env | Service | Branch (auto-deploy) | Database | URL |
|---|---|---|---|---|
| Production | `jarvis-main` (1 vCPU/2GB) | `main` | main DB | jarvis.autoworld.ro |
| Staging | `jarvis` (1 vCPU/1GB) | `staging` | staging DB | mkt-app-922ou.ondigitalocean.app |

Both `/health` endpoints return 200 (database + scheduler checks pass, ~93 ms). Production runs commit `b377661` = local `main` HEAD. July 1 had two ERROR deployments during that day's churn; the final deploy went ACTIVE and nothing has failed since.

**Issues found:**
1. **Plaintext secrets in the app spec** — `FLASK_SECRET_KEY`, both `DATABASE_URL`s (including the staging password from §1.2), and `ANAF_OAUTH_CLIENT_SECRET` are stored as `GENERAL` (cleartext, readable by any API token) instead of `SECRET` (encrypted, write-only). Convert them.
2. **Dead + corrupted env vars** — `EFACTURA_CLIENT_ID`/`EFACTURA_CLIENT_SECRET` are read by nothing (code reads `ANAF_OAUTH_*`, [oauth_service.py:35](jarvis/core/connectors/efactura/services/oauth_service.py:35)); the secret's value visibly contains a pasted "Client Secret"+tab. Delete both.
3. **No DO health checks configured** on either service despite `/health` existing and `.do/app.yaml` defining it — spec drift; DO won't gate bad deploys or auto-restart unhealthy containers.
4. **Production lacks VINCARIO keys** (staging-service-only) — VIN decode in prod can only use the nhtsa fallback. Confirm intentional.
5. When rotating the staging DB password (§1.2), update the `jarvis` service `DATABASE_URL` or staging goes down.
6. The full-access DO API token used for this check now lives in chat history — regenerate it when done.

## 5. Production database

PostgreSQL 18.4, 1.38 GB, 20/50 connections, healthy. Highlights:

- **False alarm resolved:** `crm_deals`/`crm_clients` showed 0 live tuples in stats but hold 34,879 / 35,690 real rows — statistics were reset by the PG 18 upgrade and autovacuum hasn't re-analyzed most tables. Run a manual `ANALYZE`.
- **Storage: 78% of the DB is one table's overhead.** `ai_agent.rag_documents` = 42 MB heap, **559 MB indexes, 513 MB TOAST** for 1,964 rows (~550 KB/row of index+blob weight). Likely pgvector index bloat + full document text TOASTed inline. A `REINDEX` and a look at what's stored could reclaim ~1 GB — a cost issue more than a performance one.
- Storno-split drift confirmed (§3 M5); test-drive form absence confirmed (§1.4).
